# Every Dollar Has a Name: Technical Research — User Analytics Profile (per-user cross-project usage analytics)

## Executive Summary

We are adding a personal **Usage** view to the palad-app profile that aggregates a single user's platform usage (sessions launched, workflow runs, total cost, tokens with input/output/cache breakdown, agent-type breakdown, and an activity time series) **across all projects they participate in**, filterable by time period and broken down per project. The internal design (`ai/research/technical-user-analytics-profile-2026-07-01.md`) already proposes a faithful mirror of the existing `CompanyAnalyticsService` stack, keyed off `user` instead of `company`. This external research validates that design against how AWS, GCP, OpenAI, Anthropic, GitHub, and Datadog actually build the same kind of view, and against current best practice for SQL aggregation, time-bucketing, cost/token attribution, and privacy.

**Key findings:**

1. **On-the-fly SQL aggregation is the correct v1 choice — with high confidence.** Every source agrees rollups/materialized views only pay off when query patterns are *predictable AND data is large*; the published rule of thumb is "precompute when ~80% of queries hit the same group-bys," and precomputation is documented to reduce query latency "from seconds or minutes into sub-seconds" — i.e., it earns its keep only once raw scans are genuinely slow. At palad-app's per-user, in-period, indexed scan volume, that threshold is not met. Introduce a rollup table only when a single user's in-period aggregation exceeds an interactive-latency budget (commonly cited ~hundreds of ms to low seconds). ([System Overflow](https://www.systemoverflow.com/learn/realtime-analytics-olap/pre-aggregation-patterns/when-to-use-pre-aggregation-vs-alternatives), [Hydrolix](https://hydrolix.io/glossary/summary-tables/))

2. **The "(No project)" bucket the design proposes is exactly the industry-standard pattern for unattributed usage.** The reconciliation invariant is primary-sourced from AWS: "the total charges (tagged and untagged)… reconciles with the total charges on your Bills page" — i.e., the breakdown (attributed + unattributed) must sum to the total, and untagged resources are reported, not dropped. Excluding unattributed rows from a per-scope breakdown is the documented anti-pattern. The design's `left_joins(:project)` + "(No project)" bucket is the right call; an inner join (as the company service uses) would silently break reconciliation. *Note a genuine source conflict on the end-state target:* a single blog (Vasagam, Medium confidence) argues "You'll never reach 100% attribution… [usage without metadata] either gets rejected or lands in an 'unattributed' bucket… Aim for 90%," whereas CloudZero argues the opposite ideal — "100% allocated, every dollar is attributed to an owner, with no unallocated bucket." Both views support *surfacing* an unattributed bucket; they disagree only on whether 100% is the goal. ([AWS cost allocation tags](https://docs.aws.amazon.com/awsaccountbilling/latest/aboutv2/cost-alloc-tags.html), [Medium / Vasagam](https://medium.com/@mahendran_v3/beyond-tagging-a-blueprint-for-real-time-cost-attribution-in-data-platforms-c705e8a04016), [CloudZero](https://www.cloudzero.com/blog/cloud-cost-visibility/))

3. **Discrete period presets + variable bucket granularity is exactly how the comparable consoles do it.** OpenAI's Usage API supports `bucket_width` of `1m`/`1h`/`1d`; Anthropic's usage report supports `1m`/`1h`/`1d` and the console shows hourly/minute granularity; both expose **per-token-type breakdowns** (input, output, cached/cache-read, cache-write/creation). The design's `DATE_TRUNC_KEY` (7d/30d→day, 90d→week, 1y→month) is consistent with this and avoids over-dense charts. Use Postgres `date_trunc` (already in use) and **gap-fill on the frontend or via `generate_series` LEFT JOIN** so empty buckets render as zero, not as missing points. ([OpenAI Cookbook](https://developers.openai.com/cookbook/examples/completions_usage_api), [Anthropic Usage & Cost API](https://platform.claude.com/docs/en/build-with-claude/usage-cost-api), [PopSQL generate_series](https://popsql.com/learn-sql/postgresql/how-to-use-generate-series-to-avoid-gaps-in-data-in-postgresql))

4. **Privacy: surfacing per-user spend in a team context is sensitive — but the per-user view is now industry-normal, including at Anthropic.** Anthropic ships a dedicated **Claude Code Analytics API** that returns **one record per user per day** keyed by the user's `email_address`, with per-user sessions, lines of code added/removed, commits, PRs, per-model tokens, and `estimated_cost.amount` in cents — explicitly marketed for "executive dashboards," "individual and team productivity metrics," and "cost tracking and allocation… by team." (The narrow limitation "it's not possible to break down usage or cost by individual users" survives only for the *general API Usage/Cost console surface*; the same docs now point you to the Analytics API for per-user cost.) So the precedent does **not** say a serious vendor refuses to build the per-person view — the opposite. The real guardrail comes from workforce-analytics ethics literature: per-individual metrics breed distrust unless they are **self-visible first** (the person sees their own numbers) and transparent. Our feature is the *good* shape of this — it shows a user **their own** usage on **their own** profile — but we should be deliberate about not turning it into a manager-facing per-person leaderboard without an explicit decision. ([Anthropic Claude Code Analytics API](https://platform.claude.com/docs/en/manage-claude/claude-code-analytics-api), [Anthropic Usage & Cost API FAQ](https://platform.claude.com/docs/en/build-with-claude/usage-cost-api), [WorkProdie](https://www.workprodie.com/blog/balancing-privacy-productivity-ethical-monitoring), [MiHCM](https://mihcm.com/resources/blog/ethical-issues-with-employee-monitoring-best-practices-and-compliance/))

5. **Rails specifics validate the design's index and service choices.** A composite `(user_id, created_at)` index is the canonical support for a per-user in-period range+group-by; PostgreSQL `INCLUDE`/covering indexes can make these aggregations index-only. The existing Recharts 3.8 stack is the right and already-present charting tool — no new dependency needed. Pundit `policy_scope` is the idiomatic way to enforce "only your own rows," but because the controller already scopes everything to `current_user` and never trusts a `user_id` param, an explicit policy is optional (defense-in-depth, not correctness). ([PostgreSQL covering indexes](https://www.postgresql.org/docs/current/indexes-index-only-scans.html), [oneuptime GROUP BY tuning](https://oneuptime.com/blog/post/2026-01-25-postgresql-group-by-performance/view), [Pundit](https://github.com/varvet/pundit))

**Top actionable recommendations:** (1) Ship **on-the-fly aggregation** for v1, no rollup table. (2) **Count project-less billable sessions** and surface them in an explicit **"(No project)"** bucket so the breakdown reconciles to totals. (3) Build **three slice-specific services** mirroring the company stack to avoid 3x recomputation across deferred props. (4) Ship the **read-only per-project breakdown table in v1**, and gate the interactive per-project drill-down `Select` behind a fast follow. (5) Add the composite `(user_id, created_at)` indexes now (cheap, lock-free, future-proofs the page).

## 1. Problem Framing & Research Methodology

### What we are building

palad-app users today have no cross-project view of their own usage. Project- and company-scoped analytics already exist (`CompanyAnalyticsService`, `ProjectAnalyticsService`, `AgentActivityService`, `SessionCostTokenUsageService`, etc.), but there is no "what did *I* do this month, across all my projects, and at what cost" page on the profile. The internal design (ticket #303) proposes a new personal **Usage** tab that aggregates the same metrics scoped to `current_user` across all of their `terminal_sessions` and `workflow_runs`, filterable by time period (7d/30d/90d/1y), with a per-project breakdown, an agent-type breakdown, and a daily/weekly cost+token time series. All raw data already carries `user_id`, so no new ingestion is required.

The defining wrinkle: `TerminalSession belongs_to :project, optional: true`, so a user's in-scope sessions can be **project-less** (an `agent_session`/`workflow_step` with `project_id = NULL`). Reading `user.terminal_sessions` directly (rather than anchoring on a company's projects, as the company service does) forces an explicit decision about how to count and bucket those rows so the per-project breakdown still reconciles to the summary totals.

### Why research it

The design names four open product decisions: (1) on-the-fly aggregation vs precomputed rollups for v1; (2) whether to count project-less sessions in totals (with a "No project" bucket) or exclude them; (3) one service computing all metrics vs three slice-specific services; (4) ship the per-project drill-down filter in v1 or only a read-only breakdown table. Each of these has a clear "what do mature platforms actually do" answer, and getting the attribution/bucketing decision wrong produces a dashboard whose breakdown silently does not sum to its headline total — the single most common, most embarrassing analytics bug.

### How it was researched

Live web search (July 2026) plus fetching the most authoritative primary docs. Sources span: the actual product docs for AWS Cost Explorer, GCP Cloud Billing Reports, OpenAI Usage/Cost API, Anthropic Console + Usage/Cost API + the per-user Claude Code Analytics API, GitHub Insights, and Datadog Usage Attribution (industry precedents); PostgreSQL official docs and time-series/aggregation engineering write-ups (patterns); and Rails/Pundit/Recharts material (stack-specific). Where sources conflict or a claim is uncertain, confidence is marked inline and in §7. I also read the in-repo design doc and confirmed the live frontend dependency (`recharts ^3.8.0`, already used by both existing analytics pages — `app/frontend/pages/Company/Analytics/AnalyticsPage.tsx`, `app/frontend/pages/Projects/Analytics/AnalyticsPage.tsx`).

## 2. Industry Precedents

How real products present per-user / per-scope usage and cost, and what we should copy.

### 2.1 AWS Cost Explorer — group-by + filter is the universal mental model

AWS Cost Explorer lets you **group** cost/usage by one dimension while **filtering** by others. Native group-by dimensions include Service, Linked (member) Account, Usage Type, API Operation, Availability Zone, Purchase Option, **Tag**, and **Cost Category**; you can "view your daily/monthly cost grouped by member accounts to understand who is driving your most cost." A key UX detail directly relevant to our per-project breakdown: **the chart shows the top N (9) groups and aggregates the remainder into a 10th bucket**, while the data table below breaks out the individual rows. ([AWS Cost Explorer — what is it](https://docs.aws.amazon.com/cost-management/latest/userguide/ce-what-is.html), [Cost Explorer chart](https://docs.aws.amazon.com/cost-management/latest/userguide/ce-chart.html), [More filtering/grouping dimensions](https://aws.amazon.com/blogs/aws/aws-cost-explorer-update-more-filtering-and-grouping-dimensions/))

**Takeaway for us:** "group by project, filter by period/user" is the same shape as Cost Explorer's "group by account, filter by service/tag." The top-N + "Other" rollup pattern is worth keeping in mind if a power user has dozens of projects (our v1 table can simply scroll; the top-N chart trick is a known refinement).

### 2.2 GCP Cloud Billing Reports — group by Project / Service / SKU / Label

GCP's Reports page plots usage cost across all projects in a billing account and lets you **group by Project, Service, SKU, Location, or Label**, with filters on the same dimensions. The default preset is "current month's daily cost grouped by Service." Labels are explicitly framed as the mechanism for fine-grained cost attribution ("group by label, choose the key"). ([GCP Cloud Billing Reports — how-to](https://docs.cloud.google.com/billing/docs/how-to/reports), [Reports overview](https://docs.cloud.google.com/billing/docs/reports))

**Takeaway for us:** GCP's "group by Project" within a billing account is the closest 1:1 analog to our per-project breakdown within a user's footprint. Time bucketing defaults to **daily over the current month** — consistent with our 30d→daily default.

### 2.3 OpenAI Usage & Cost APIs — the per-user, per-token-type reference design

This is the most directly relevant precedent because it is LLM-usage attribution, exactly our domain. The **Usage API** supports `bucket_width` of **`1m` / `1h` / `1d`** (default `1d`) and `group_by` of **`model`, `project_id`, `user_id`, `api_key_id`**. Token metrics are broken down into **`input_tokens`, `output_tokens`, `input_cached_tokens`, `input_audio_tokens`, `output_audio_tokens`, `num_model_requests`**. The **Cost API** is the financial counterpart: it currently supports only **`1d`** buckets and groups by **`line_item`** and **`project_id`**, returning monetary amounts. The Usage dashboard UI explicitly supports a **"Daily usage breakdown" dropdown to view a particular user**, and **top-users-in-organization** breakdowns, with CSV export. ([OpenAI Usage API dashboard](https://help.openai.com/en/articles/10478918-api-usage-dashboard), [OpenAI Cookbook — Usage & Cost API](https://developers.openai.com/cookbook/examples/completions_usage_api), [Usage API announcement](https://community.openai.com/t/introducing-the-usage-api-track-api-usage-and-costs-programmatically/1043058))

**Takeaways for us (high value):**
- **Per-user is a first-class grouping dimension at OpenAI** — they expose `user_id` group-by. Our feature is the same idea, just self-service.
- **Token breakdown is the norm, not a luxury.** OpenAI separates input / output / cached. This supports the issue's "input/output/cache breakdown" requirement and argues for at least *capturing* the split (we already store `input_tokens`, `output_tokens`, `cache_write_tokens`, `cache_read_tokens` in `usage_statistics`).
- **Usage (tokens) and Cost (money) are modeled as related-but-distinct surfaces** with different bucket granularities (cost is coarser, daily-only). Our single time series carrying both `cost_cents` and `total_tokens` per bucket is fine for v1; just be aware the two can warrant different granularities at scale.

### 2.4 Anthropic — workspace-level Usage/Cost API plus a per-user Claude Code Analytics API

Anthropic's Console Usage page filters by **Workspace, Model, Time Period (months → days), and API Key**, showing input/output token bar charts at hourly/minute granularity plus cache-rate. The Cost page breaks spending down by **Workspace, Model, Month**. The programmatic **Usage Report API** (`/v1/organizations/usage_report/messages`) supports **`1m`/`1h`/`1d`** buckets and tracks **uncached input, cached input, cache creation (write), and output tokens**, groupable by API key, workspace, model, service tier, context window, etc. The **Cost Report API** (`/v1/organizations/cost_report`) reports USD (daily-only buckets) and groups by **workspace or description**. ([Anthropic Usage & Cost API](https://platform.claude.com/docs/en/build-with-claude/usage-cost-api))

**The general API Usage/Cost surface scopes to workspace, not person** — its docs note "it's not possible to break down usage or cost by individual users" *for that surface* (large numbers of API keys make per-key cost expensive). But this is **not** a privacy stance, and it is no longer the whole picture (see §2.4a). The same FAQ now answers "How do I get per-user cost breakdowns for Claude Code?" by pointing to the Claude Code Analytics API. So the only safe reading is the narrow one: the *workspace-level* console/API does not split by individual; a separate, dedicated API does. (High confidence on the quoted limitation and its narrow scope.)

### 2.4a Anthropic Claude Code Analytics API — the single closest analog to this feature

This is the most on-point precedent in the entire survey: a major LLM vendor's **per-user, per-day, cross-context coding-usage** surface with cost and tokens — almost exactly what feature #303 builds. The `/v1/organizations/usage_report/claude_code` endpoint returns **one record per user per day**. Each record is keyed by an `actor` (`user_actor` carrying an `email_address`, or `api_actor` with an `api_key_name`) and carries per-user **`num_sessions`**, **`lines_of_code.added`/`removed`**, **`commits_by_claude_code`**, **`pull_requests_by_claude_code`**, per-tool accept/reject counts (Edit/MultiEdit/Write/NotebookEdit), and a **per-model breakdown** with `tokens.input/output/cache_read/cache_creation` and **`estimated_cost.amount`** (in cents USD). Anthropic markets it explicitly for **"Executive dashboards,"** **"Developer productivity analysis: Track individual and team productivity metrics over time,"** and **"Cost tracking and allocation: …allocate costs by team or project."** ([Anthropic Claude Code Analytics API](https://platform.claude.com/docs/en/manage-claude/claude-code-analytics-api))

**Takeaways for us (high value):**
- **Per-user, per-day, cost+tokens+activity is an industry-standard shape now** — the design's per-user mirror of the company stack is squarely in line with how a leading vendor models the same problem.
- **Daily aggregation is the grain.** Anthropic aggregates to one row per user per UTC day — consistent with our day-level default bucketing for short ranges.
- **Cost is reported in cents, alongside a token breakdown** — matching our decision to keep `cost_cents` authoritative with the token split as an explanatory drill-down (§3.3).
- **This precedent reverses the old "vendors won't build per-person" framing** used elsewhere in early drafts: a per-person view exists and is sold for manager/executive use. The *ethics* guardrail (self-visibility first; transparency) therefore has to stand on its own merits (§3.4), not on an appeal to vendor abstention.

### 2.5 GitHub Insights — activity, not money; per-contributor breakdowns exist

GitHub's org Insights dashboard provides **weekly/monthly/yearly** visualizations of "how your organization is getting work done," and exposes **per-contributor** activity (contribution calendar, repo contribution graph, commits/PRs/issues per individual), plus discussion insights with **daily unique contributors** counts. ([GitHub org insights](https://docs.github.com/en/organizations/collaborating-with-groups-in-organizations/viewing-insights-for-your-organization), [contributors page](https://docs.github.com/en/repositories/viewing-activity-and-data-for-your-repository/viewing-a-projects-contributors), [discussion insights](https://docs.github.com/en/discussions/managing-discussions-for-your-community/viewing-insights-for-your-discussions))

**Takeaway for us:** GitHub *does* surface per-person activity (commits, contributions) at org scope, and the time grain is week/month/year presets — same family as our 7d/30d/90d/1y. It normalizes a personal activity time series and per-person breakdowns *as long as the metric is "what I produced," not a surveillance feed*.

### 2.6 Datadog Usage Attribution — the tag-based "who spent it" model + the 3-key cap

Datadog's Usage Attribution breaks usage down by **up to three tag keys** (e.g., `team`, `env`), summarizes monthly + hourly, visualizes usage over time per tag, and exports CSV — explicitly to support **chargeback/showback** and "identify which teams or services generate the most monitoring costs." ([Datadog Usage Attribution](https://docs.datadoghq.com/account_management/billing/usage_attribution/), [estimated usage metrics](https://docs.datadoghq.com/account_management/billing/usage_metrics/))

**Takeaways for us:** (1) The whole attribution model is tag-driven, and there is a documented **cardinality cap** (3 tag keys) — a reminder that breakdown dimensions are deliberately bounded, not infinite. Our breakdown dimensions are fixed and small (project, agent_type, time bucket), which is the right discipline. (2) Datadog frames this as showback/chargeback — a *team accountability* lens — which is the lens we are explicitly **not** leading with (we lead with personal self-visibility).

### 2.7 Cross-precedent synthesis

The consensus is unambiguous: **group-by-one-dimension + filter-by-period**, a **handful of fixed breakdown dimensions**, **discrete period presets with coarser bucketing at longer ranges**, a **per-token-type breakdown for LLM usage**, and **an explicit unattributed bucket that makes the breakdown reconcile to the total**. The palad-app design already matches all of these.

## 3. Patterns & Pitfalls

### 3.1 On-the-fly aggregation vs precomputed rollups — when to switch

**The pattern (recommended for v1): on-the-fly SQL aggregation.** Compute `GROUP BY` + `SUM`/`COUNT` directly against `terminal_sessions`/`usage_statistics`/`workflow_runs`, filtered by `user_id` and `created_at`, at request time. This is what the existing project/company analytics already do in production.

**When rollups/materialized views/time-series tables become worth it:** the literature is consistent that precomputation pays off only when **query patterns are predictable AND raw queries are genuinely expensive.** Concretely:
- "Precomputed aggregations work best when query patterns are predictable and repetitive — for example, if **80% of queries hit the same group-by combinations**." ([System Overflow](https://www.systemoverflow.com/learn/realtime-analytics-olap/pre-aggregation-patterns/when-to-use-pre-aggregation-vs-alternatives))
- The payoff is a latency win on slow scans: summary tables "drastically reduce the amount of data scanned and processed per query… often reducing the latency of queries from seconds or minutes into sub-seconds." The corollary is that the win is meaningful only when raw queries are *already* in the seconds-to-minutes range — not for a fast indexed scan. ([Hydrolix summary tables](https://hydrolix.io/glossary/summary-tables/))
- Choose **on-the-fly** when "query patterns are highly exploratory and unpredictable" or "dimensions change frequently" (maintaining rollups becomes "a maintenance nightmare… every schema change requires rebuilding aggregates"). ([System Overflow](https://www.systemoverflow.com/learn/realtime-analytics-olap/pre-aggregation-patterns/when-to-use-pre-aggregation-vs-alternatives))

**Anti-pattern:** building a rollup table *before* you have evidence the live query is slow. It adds an ingestion/refresh path, a freshness-vs-accuracy tradeoff, and reconciliation risk (rollup drifts from raw) — all of which the issue explicitly wants to avoid ("no new ingestion infrastructure"). Confidence: **High** that on-the-fly is right for v1.

**If/when we do need rollups, the options (in increasing complexity):**
1. **Materialized view, refreshed on a schedule.** Simple, but `REFRESH MATERIALIZED VIEW` **recomputes the entire query** — "refresh time scales with total data size… a view over 100 million rows takes the same time to refresh whether 10 or 10 million rows changed." `REFRESH … CONCURRENTLY` avoids read-blocking but **requires a unique index** and is slower + causes bloat. ([PostgreSQL REFRESH MATERIALIZED VIEW](https://www.postgresql.org/docs/current/sql-refreshmaterializedview.html), [Tiger Data](https://www.tigerdata.com/blog/materialized-views-the-timescale-way))
2. **A plain rollup table** (`daily_user_usage`) populated incrementally by a nightly/append job — the most Rails-idiomatic. Pitfall: late-arriving/edited `usage_statistics` rows; reconcile periodically.
3. **TimescaleDB continuous aggregates** — incremental, auto-updated, only recomputes changed buckets. Powerful but adds a Postgres extension dependency we do not currently have; over-engineered for v1. ([oneuptime continuous aggregates](https://oneuptime.com/blog/post/2026-01-27-timescaledb-continuous-aggregates/view))

**A hybrid is the natural end-state, not the start:** keep a small set of precomputed summary tables for the hot, predictable group-bys and fall back to on-the-fly aggregation for everything else. But that is a scale-driven optimization to reach *after* the live query is demonstrably slow — v1 should be pure on-the-fly. ([System Overflow](https://www.systemoverflow.com/learn/realtime-analytics-olap/pre-aggregation-patterns/when-to-use-pre-aggregation-vs-alternatives))

### 3.2 Time-bucketing 7d/30d/90d/1y with variable granularity

**Pattern:** map each period preset to a `date_trunc` granularity so charts stay legible — exactly the design's `DATE_TRUNC_KEY` (7d/30d→`day`, 90d→`week`, 1y→`month`). This mirrors OpenAI's `1m`/`1h`/`1d` tiering and GCP's daily-over-a-month default. `date_trunc` "truncates a TIMESTAMP based on a date part (hour, week, month)" and is the standard tool absent TimescaleDB. ([Tiger Data time_bucket vs date_trunc](https://www.tigerdata.com/blog/simplified-time-series-analytics-using-the-time_bucket-function))

**Pitfall (the big one): gaps.** Grouping only rows that exist produces a series **missing the empty buckets** — a chart that skips days with no activity, distorting trends. The fix is gap-filling: build a complete timeline with `generate_series` and `LEFT JOIN` the aggregates, using `COALESCE(..., 0)` so empty buckets render as zero. ([PopSQL generate_series](https://popsql.com/learn-sql/postgresql/how-to-use-generate-series-to-avoid-gaps-in-data-in-postgresql), [oneuptime generate time series](https://oneuptime.com/blog/post/2026-01-25-postgresql-generate-time-series/view)) TimescaleDB's `time_bucket_gapfill()` (+ `locf()`/`interpolate()`) does this natively but requires the extension. For our scale, **gap-filling on the frontend** (iterate the expected buckets in JS, default missing to 0) is the lowest-friction option and is what the existing Recharts pages effectively rely on; if the BE should own it, the `generate_series` LEFT JOIN is the portable approach. Confidence: **High** that gaps must be handled; **Medium** on FE-vs-BE placement (a judgement call — the design currently emits only non-empty buckets, which is the one thing to fix or consciously accept).

**Pitfall: time zones and week-start.** `date_trunc('week', ...)` truncates to **Monday** in Postgres and operates in the session time zone; "this week" can be off-by-a-day for users in other zones, and week boundaries can disagree with what a user expects. The `groupdate` gem exists precisely to handle "time zone conversions, including daylight saving" and configurable `week_start`. We are not adopting groupdate (we use raw `date_trunc`), so the **decision to make explicit** is which time zone the buckets are computed in (UTC vs. user-local) — pick one and be consistent. ([groupdate](https://github.com/ankane/groupdate)) Confidence: **High** that this is a real trap; **Medium** on materiality for our v1 (UTC is an acceptable v1 choice if stated).

### 3.3 Cost & token attribution, and the reconciliation invariant

**Pattern — the reconciliation invariant (primary source):** the entire FinOps discipline is built on the principle that **attributed + unattributed must reconcile to the total.** AWS states it verbatim: "At the end of the billing cycle, the total charges (tagged and untagged) on the billing report with cost allocation tags reconciles with the total charges on your… Bills page total." The AWS cost-allocation report "includes both tagged and untagged resources" — the untagged remainder is *reported*, not dropped. ([AWS cost allocation tags](https://docs.aws.amazon.com/awsaccountbilling/latest/aboutv2/cost-alloc-tags.html))

**A real source conflict on whether 100% is achievable — flagged, not glossed.** A single practitioner blog (Vasagam, Medium confidence) argues you should *expect* an unattributed remainder: "You'll never reach 100% attribution… [an untagged query] either gets rejected or lands in an 'unattributed' bucket that you review manually… Aim for 90% — the last 10% has diminishing returns." ([Vasagam — real-time cost attribution](https://medium.com/@mahendran_v3/beyond-tagging-a-blueprint-for-real-time-cost-attribution-in-data-platforms-c705e8a04016)) CloudZero argues the **opposite ideal** — that complete visibility means "100% allocated, every dollar is attributed to an owner, with no unallocated bucket," and notes that while 87% of orgs use tagging they "on average allocate just 75% of cloud costs." ([CloudZero cost visibility](https://www.cloudzero.com/blog/cloud-cost-visibility/)) These conflict on the *target* (accept a residual bucket vs. drive it to zero) but **agree on the mechanic that matters for us**: you surface the unattributed slice explicitly so the breakdown reconciles to the total. For palad-app, project-less sessions are genuinely un-attributable to a project (the FK is nullable by design), so we surface them rather than chase 100% — the Vasagam stance fits our data, while CloudZero's ideal is about better *tagging*, which doesn't apply to an inherently-optional association.

**This is the single most important external validation for our design.** Our "(No project)" bucket *is* the unattributed bucket. The design's `left_joins(:project)` + unconditional "(No project)" row guarantees `sum(projectBreakdowns) == totals`. Using an **inner join** (as `CompanyAnalyticsService` does — it can, because it anchors on `projects.company_id` which forces a project) would silently drop project-less rows and **break reconciliation** (`sum(breakdown.sessions) < total_sessions`). That is the documented anti-pattern. Confidence: **High**.

**Pattern — token type attribution.** LLM usage must distinguish token classes because they are **priced differently**: cache reads cost ~10% of input price (a 90% discount at Anthropic); cache writes cost *more* than base input (1.25× for 5-min TTL, 2× for 1-hour at Anthropic); output is priced separately from input. So **"total tokens" alone is a lossy metric for cost reasoning** — two users with identical total tokens can have very different costs depending on cache-hit ratio. ([Artificial Analysis — prompt caching](https://artificialanalysis.ai/models/caching), [Anthropic prompt caching](https://platform.claude.com/docs/en/build-with-claude/prompt-caching), [CloudZero Claude pricing](https://www.cloudzero.com/blog/claude-api-pricing/)) Our `usage_statistics` already stores the four-way split (`input_tokens`, `output_tokens`, `cache_write_tokens`, `cache_read_tokens`), and the canonical SQL expression sums them with a legacy-`tokens` fallback. **Recommendation:** keep `cost_cents` as the authoritative cost number (it already reflects the per-type pricing), and treat the token breakdown as an *explanatory* drill-down, not as a cost proxy.

**Pitfall — averages that don't reconcile.** Avg-cost-per-session computed as `total_cost / total_sessions` will differ from `sum(per_project_cost) / sum(per_project_sessions)` when buckets have different cost densities (Simpson's-paradox-style). The design already documents this and matches existing company behavior — fine, just don't display two avgs that visibly disagree.

### 3.4 Privacy & visibility of per-user usage/spend

**Pattern — self-visibility first, transparency always.** The ethics literature converges on: aggregate over individuals where possible; when you do show per-person data, make it **transparently accessible to the employees themselves**, not just leadership; and always disclose what's collected and who can see it. "Ethical monitoring focuses on aggregate analytics… rather than individual behaviours"; "modern workforce analytics tools should be **transparently accessible to both leadership and employees themselves**"; "the top ethical concern is a lack of transparency." 45% of monitored employees report negative mental-health effects from surveillance tooling. ([WorkProdie](https://www.workprodie.com/blog/balancing-privacy-productivity-ethical-monitoring), [MiHCM](https://mihcm.com/resources/blog/ethical-issues-with-employee-monitoring-best-practices-and-compliance/), [ActivTrak](https://www.activtrak.com/solutions/employee-monitoring/ethical-considerations/))

**Precedent (no longer cautionary):** an earlier reading of this doc leaned on "Anthropic's Console does not let you break usage/cost down by individual user" as evidence that a serious vendor chose *not* to build the per-person view. That generalization is wrong. Anthropic ships a dedicated **Claude Code Analytics API** that breaks usage, productivity, and **cost (in cents)** down **per user per day** by `email_address`, and markets it for executive dashboards and team cost allocation (§2.4a). The "not by individual users" limitation applies only to the *general* workspace-level Usage/Cost surface, and the same docs now redirect per-user-cost questions to the Analytics API. So vendor behavior does **not** argue against a per-person view; if anything it normalizes one. The ethics argument below therefore rests on the workforce-analytics literature alone (all Medium-confidence sources), not on an appeal to vendor abstention. ([Anthropic Claude Code Analytics API](https://platform.claude.com/docs/en/manage-claude/claude-code-analytics-api), [Anthropic Usage & Cost API FAQ](https://platform.claude.com/docs/en/build-with-claude/usage-cost-api))

**How this maps to us — favorably:** our feature is the *good* shape: the user sees **their own** numbers on **their own** profile (self-visibility). It is leak-proof by construction because everything is scoped to `current_user` (the controller never trusts a `user_id` param). The **pitfall to avoid** is scope creep into a **manager/admin-facing per-person leaderboard** (which Story 12.3 "Cost Breakdown by User" hints at) without an explicit decision — that flips the feature from self-visibility to surveillance. **Recommendation:** ship the personal self-view now; treat any admin "cost per user" cross-person view as a *separate, explicitly-decided* feature with its own authorization (admin-only) and ideally team-norm transparency. Confidence: **High** on the principle; **Medium** on how strictly to apply it (depends on whether palad-app's customers expect manager visibility).

**Security pitfall:** the classic IDOR — a per-user analytics endpoint that accepts a `user_id` param and forgets to authorize it leaks other users' spend. We avoid this entirely by deriving the user from the session (`current_user`), which is the safest pattern ("scope before find"). ([Pundit best practices](https://www.shakacode.com/blog/mastering-authorization-in-rails-with-pundit/))

### 3.5 Service decomposition pitfall

**Anti-pattern:** one service that computes *all* metrics, invoked once per deferred prop. With three deferred blocks each calling `Service.new(...).call`, and `call` recomputing every metric, you do **~3× the aggregate-query work** the page needs. The company stack deliberately avoids this by wiring **three distinct services** (`CompanyAnalyticsService`, `CompanyAgentActivityService`, `CompanySessionCostTokenUsageService`), each computing only its slice. This is a Rails/Inertia-specific trap: `InertiaRails.defer` evaluates each block independently, so a "compute everything" service is silently re-run per block. **Pattern:** mirror the company stack with slice-specific services (or, second-best, give one service per-metric methods so each block runs only its query). Confidence: **High** (this is an in-repo, observable cost, corroborated by the existing company architecture).

## 4. Concrete Libraries & Approaches (Rails + Pundit + React/Inertia/Mantine + Postgres)

### 4.1 Aggregation in Rails/Postgres — stick with raw ActiveRecord `group`/`pick`/`pluck`

The existing services use ActiveRecord `group(...).pluck(SUM(...))` / `.pick(...)` against raw SQL fragments — this is the right tool and matches "do the work in the database." Notes from the research:
- **`group().count` loads the full grouped result into a Ruby hash**; for tens/hundreds of thousands of groups this is a memory risk. Our group cardinality is tiny (projects-per-user, ~4 agent types, ≤365 time buckets), so this is a non-issue here — but it's why we should *not* generalize this service to high-cardinality group-bys. ([ReviewInsights / GROUP BY + COUNT guide](https://openillumi.com/en/en-rails-activerecord-groupby-count/), [ActiveRecord::Calculations](https://api.rubyonrails.org/classes/ActiveRecord/Calculations.html))
- Push aggregation to SQL, never materialize rows into Ruby to sum them. ([Haseeb — Rails + Postgres count performance](https://haseebeqx.com/posts/cheat-sheet-for-rails-postgresql-count-performance/))

**No new gem needed.** `groupdate` is the popular gem for this, but it's designed for Chartkick and adds a dependency; the repo already does time-bucketing with raw `date_trunc` and renders with Recharts, so adopting groupdate would be churn for no gain. (Mentioned for completeness; **not recommended**.) ([groupdate](https://github.com/ankane/groupdate))

### 4.2 Indexing — composite `(user_id, created_at)` + optional covering index

The per-user, in-period group-bys filter on `user_id` (equality) and `created_at` (range). The canonical support is a **composite index leading with the equality column then the range column**: `(user_id, created_at)`. The existing `user_id`-leading indexes cover equality lookups but **none leads with `(user_id, created_at)`**, so the planner can't use one index for both the filter and the range. The design's migration (`add_index :terminal_sessions, %i[user_id created_at]` with `algorithm: :concurrently, if_not_exists: true`, mirrored on `workflow_runs`) is exactly right and lock-free. ([oneuptime — optimize GROUP BY](https://oneuptime.com/blog/post/2026-01-25-postgresql-group-by-performance/view))

**Going further (optional, future):** PostgreSQL **covering indexes** via `INCLUDE` can make these aggregations **index-only scans** (answer the query from the index without touching the heap) — e.g., `CREATE INDEX ... ON terminal_sessions (user_id, created_at) INCLUDE (project_id, agent_type, cost_cents, total_tokens)`. Caveats from the docs: index-only scans need the table's **visibility map** to be mostly set (works best on **infrequently-updated** tables; `terminal_sessions` is updated as sessions run, so the benefit is partial), and the wider index costs write/space. **Recommendation:** add the plain `(user_id, created_at)` composite now; consider the covering variant only if EXPLAIN shows heap fetches dominating after the basic index. ([PostgreSQL — index-only scans & covering indexes](https://www.postgresql.org/docs/current/indexes-index-only-scans.html), [PostgreSQL wiki — index-only scans](https://wiki.postgresql.org/wiki/Index-only_scans)) Confidence: **High** on the composite index; **Medium** on the covering index's payoff given session-table write churn.

### 4.3 Authorization — Pundit `policy_scope` is idiomatic, but optional here

Pundit's **`policy_scope`** is the standard way to enforce "a user only sees their own/permitted rows" at the query level, and the safest habit is **"scope before find"** (`policy_scope(Model).find(...)`) so unauthorized rows are never even loaded. ([Pundit](https://github.com/varvet/pundit), [ShakaCode — mastering Pundit](https://www.shakacode.com/blog/mastering-authorization-in-rails-with-pundit/)) However, our `ProfileController` derives the user from the session (`current_user`) and never accepts a `user_id` param, so the data is **intrinsically scoped** — there is no untrusted input to authorize. This matches how `ProfileController` already manages credentials without Pundit. **Recommendation:** rely on `require_auth` + `current_user` scoping for v1 (correct and leak-proof); add a trivial `ProfilePolicy#usage? = true` only if reviewers want symmetry with `Web::Company::AnalyticsPolicy`. The Pundit scope pattern becomes **mandatory** only if/when an admin-facing "cost per user" cross-person view (Story 12.3) is built — that endpoint *does* take a target user and *must* be authorized. Confidence: **High**.

### 4.4 Frontend — Recharts 3.8 (already present), reuse the existing panels

The repo already depends on **`recharts ^3.8.0`** (confirmed in `package.json`) and both existing analytics pages (`Company/Analytics/AnalyticsPage.tsx`, `Projects/Analytics/AnalyticsPage.tsx`) render with it. The library-comparison literature positions Recharts as a common default for React dashboards (declarative component API, SVG rendering, trims its bundle by using "lightweight D3 submodules instead of the entire D3 library"), heavier than primitive libraries like visx (which Querio puts at "about 12.3 kB") — but since Recharts is already in the bundle, the marginal cost of reusing it is **zero** and switching would be pure churn. (Note: a specific gzipped byte figure for Recharts is not cited here — the comparison sources discuss its bundle qualitatively, not with a single agreed number — but the recommendation does not depend on it, since reuse is justified by the existing dependency alone.) ([Querio — top React chart libraries](https://querio.ai/articles/top-react-chart-libraries-data-visualization), [LogRocket — best React chart libraries 2026](https://blog.logrocket.com/best-react-chart-libraries-2026/)) The design's plan to **port the existing panels** (summary stat grid, per-project table, agent pie, daily cost/token area charts) and **re-type them against a new `Props`** (dropping `scope`) is the correct reuse strategy; extracting shared formatters (`formatCostCents`, `formatTokens`, `tickIntervalForPeriod`) into `shared/lib` is a nice-to-have. Confidence: **High**.

### 4.5 Inertia deferred props — match the existing streaming convention

The existing pages wrap each metric in `InertiaRails.defer(group: ...)` so the shell paints immediately and panels stream in. The new Usage page should mirror this with `group: "usage"`. The §3.5 decomposition pitfall applies directly here: because each deferred block is evaluated independently, **back each block with its own slice service** so no block recomputes another's aggregates. (In-repo convention; corroborated by `analytics_controller.rb` and the company service trio.)

## 5. Recommendations for palad-app

Tied directly to the internal design (`ai/research/technical-user-analytics-profile-2026-07-01.md`):

1. **Ship on-the-fly SQL aggregation for v1; no rollup table.** Validated by the precompute-only-when-predictable-and-expensive consensus (§3.1). Add a §8-style note: introduce a `daily_user_usage` rollup table (or materialized view) only if a single user's in-period aggregation breaches an interactive-latency budget after the `(user_id, created_at)` index is in place. (High confidence.)

2. **Count project-less billable sessions and surface a "(No project)" bucket.** This is the FinOps-standard unattributed bucket (§3.3). Use `left_joins(:project)` (not the company service's inner join) so `sum(projectBreakdowns) == totals` holds for sessions, cost, and tokens. Enforce with the reconciliation test the design already specifies. (High confidence.)

3. **Mirror the company stack with three slice-specific services**, not one all-metrics service, to avoid 3× recomputation across the three deferred props (§3.5). (High confidence.)

4. **Ship the read-only per-project breakdown table in v1; gate the interactive drill-down `Select` behind a fast follow.** The breakdown table is the AC and the universally-present view (AWS/GCP group-by); the interactive per-project filter is a refinement (analogous to Cost Explorer filtering to one project), not a launch blocker. The service already supports `project_id`, so the drill-down is a small additive change later. (Medium-High confidence — this is a scope/sequencing judgement, but the precedent supports "breakdown first, filter later.")

5. **Add the composite `(user_id, created_at)` indexes now** on `terminal_sessions` and `workflow_runs`, concurrently + `if_not_exists` (lock-free, idempotent). It's the exact support for the page's hot query and future-proofs it. Defer the covering/`INCLUDE` variant until EXPLAIN justifies it. (High confidence.)

6. **Keep `cost_cents` as the authoritative cost; treat the input/output/cache token split as an explanatory drill-down**, not a cost proxy (§3.3 — cache reads/writes are priced very differently). For v1, total-token parity with the company page is acceptable; if PM wants the explicit 3-way token chart (issue's "input/output/cache breakdown"), it's additive (extra columns on the time-series struct + one chart). (High confidence on the principle; the chart itself is OQ-3.)

7. **Handle empty time buckets.** Decide explicitly: either gap-fill on the frontend (iterate expected buckets, default 0) or via a `generate_series` LEFT JOIN on the backend. Don't ship a series that silently omits zero-activity days. (High confidence it must be addressed.)

8. **Pick and document the bucketing time zone** (UTC is fine for v1; just be consistent and aware week-start = Monday in Postgres). (Medium confidence on materiality.)

9. **Privacy posture: lead with self-visibility.** This personal self-view is the privacy-respecting shape and needs no special gating beyond `require_auth`. Note the bar here is *lower* than an early draft assumed: a per-user cost+productivity view is now an industry-normal product (Anthropic's Claude Code Analytics API ships exactly that, sold for manager/executive dashboards — §2.4a), so a cross-person view is not taboo by precedent. The guardrail is ethics-of-monitoring, not vendor practice: if/when Story 12.3 ("Cost Breakdown by User", admin-facing, cross-person) is built, treat it as a separate feature with admin-only Pundit authorization (`policy_scope`) and a deliberate team-transparency decision (disclose what's collected and who can see it) — do not let the personal view quietly grow a manager leaderboard without that decision. (High confidence on the self-view boundary; Medium on how strict to be on the cross-person view — customer/culture-dependent, and the ethics sources are all Medium.)

10. **Authorization for v1: no Pundit policy required** (intrinsic `current_user` scoping, no untrusted `user_id`), consistent with the rest of `ProfileController`. Add a no-op `ProfilePolicy#usage?` only for reviewer symmetry. (High confidence.)

## 6. Open Decisions Informed by Research

### 6.1 On-the-fly aggregation vs precomputed rollups for v1
**Recommendation: on-the-fly aggregation. Confidence: High.** Precomputation pays off only when query patterns are predictable *and* raw queries are expensive (the "~80% of queries hit the same group-bys" regime, and where precompute takes scans "from seconds or minutes into sub-seconds") — neither holds for a per-user, indexed, in-period scan at our volume. Rollups add ingestion, freshness, and reconciliation risk the issue explicitly wants to avoid. Revisit only when EXPLAIN/latency on the live query (post-index) shows it exceeding an interactive budget; then prefer a simple incremental rollup table over a full-recompute materialized view. ([System Overflow](https://www.systemoverflow.com/learn/realtime-analytics-olap/pre-aggregation-patterns/when-to-use-pre-aggregation-vs-alternatives), [Hydrolix](https://hydrolix.io/glossary/summary-tables/), [PostgreSQL REFRESH MV](https://www.postgresql.org/docs/current/sql-refreshmaterializedview.html))

### 6.2 Count project-less sessions (with a "No project" bucket) or exclude them
**Recommendation: count them, in an explicit "(No project)" bucket. Confidence: High.** This is the industry-standard *unattributed bucket*. The reconciliation invariant is verbatim in AWS's primary docs ("the total charges (tagged and untagged)… reconciles with the total charges on your Bills page") and the report "includes both tagged and untagged resources" rather than dropping the remainder. Excluding project-less rows would under-count the user's real "sessions launched" and is the documented anti-pattern. Implementation: `left_joins(:project)` + unconditional "(No project)" row so `sum(breakdown) == totals` for sessions, cost, and tokens; lock it in with the reconciliation test. (Practitioner blogs differ on whether 100% attribution is achievable — Vasagam says accept a residual bucket; CloudZero says drive it to zero — but both surface the bucket; our project-less rows are inherently un-attributable, so we surface them. See the §7 conflict note.) ([AWS cost allocation tags](https://docs.aws.amazon.com/awsaccountbilling/latest/aboutv2/cost-alloc-tags.html), [Vasagam](https://medium.com/@mahendran_v3/beyond-tagging-a-blueprint-for-real-time-cost-attribution-in-data-platforms-c705e8a04016), [CloudZero](https://www.cloudzero.com/blog/cloud-cost-visibility/))

### 6.3 Three slice-specific services vs one service computing all metrics
**Recommendation: three slice-specific services (mirror the company stack). Confidence: High.** Because `InertiaRails.defer` evaluates each block independently, a single all-metrics service is re-run once per deferred prop and recomputes every metric — ~3× the aggregate work the page needs. The company stack already solves this with three distinct services, each computing only its slice. Faithful mirror + lowest cost. (Second-best if minimizing files matters: one service with per-metric methods so each block runs only its query.) (In-repo architectural evidence; general "do the work in the database, once" principle — [ActiveRecord::Calculations](https://api.rubyonrails.org/classes/ActiveRecord/Calculations.html).)

### 6.4 Ship per-project drill-down (project filter) in v1, or only a read-only breakdown table
**Recommendation: read-only breakdown table in v1; interactive drill-down `Select` as a fast follow. Confidence: Medium-High.** The per-project breakdown table is the AC and the view every comparable product ships (AWS "group by account/service," GCP "group by project"); the interactive single-project filter is the *refinement* layer (Cost Explorer's "filter to one project"), valuable but not a launch blocker. The service already accepts `project_id`, so adding the `Select` later is a small additive change with no contract break. This sequencing matches "show the breakdown first, let users filter into it second." ([AWS Cost Explorer chart](https://docs.aws.amazon.com/cost-management/latest/userguide/ce-chart.html), [GCP Billing Reports](https://docs.cloud.google.com/billing/docs/how-to/reports)) Note: this is a product-sequencing call; the precedent supports it but doesn't mandate it.

### Conflicting-source notes
- **Per-user attribution as a product surface (corrected):** OpenAI exposes `user_id` grouping (source 8/9); Anthropic's *general* Usage/Cost API does not split by individual (source 10/11) **but its Claude Code Analytics API does** — per user per day, with cost in cents (source 11a). So there is *no* vendor disagreement that per-user attribution is legitimate — both leading LLM vendors ship it. This corrects an earlier draft that read Anthropic as "deliberately not building the per-person view": that claim was scoped too broadly and is refuted by source 11a. Resolution for us: our feature (a user seeing their own data) is the self-service shape and is well-precedented; any *cross-person admin* view is also precedented (Anthropic markets exactly that), but should still carry an explicit authorization + transparency decision on **ethics** grounds (sources 30–32), not because vendors avoid it.
- **Attribution target — genuine conflict (sources 25 vs 26):** Vasagam (source 26, Medium) says you can never reach 100% attribution and should accept a residual "unattributed" bucket (Aim for 90%); CloudZero (source 25, High) argues the ideal is 100% allocation with "no unallocated bucket." They disagree on the *goal* but agree on the *mechanic we use* — surface the unattributed slice so the breakdown reconciles to the total. The reconciliation invariant itself is independently anchored on the AWS primary source (source 4, verbatim). For palad-app, project-less sessions are inherently un-attributable (nullable FK by design), so the residual-bucket stance (Vasagam) fits; CloudZero's 100% ideal is about tagging discipline, which doesn't map to an optional association.
- **Bucket granularity for cost vs usage:** OpenAI's Usage API allows 1m/1h/1d but its **Cost API is 1d-only** (source 8); Anthropic's Cost Report API is likewise 1d-only (source 11). Minor tension with our single time series carrying both cost and tokens at one granularity. Resolution: acceptable for v1; if we ever need finer token granularity than cost, split the series.
- **Gap-filling placement (FE vs BE):** sources describe both `generate_series`/`time_bucket_gapfill` (BE) approaches (23/24) and the general need to render zeros; none mandates a layer. Marked Medium — a deliberate choice for us to make.
